# 「已看过」名单设计（watched）

- 日期：2026-10-17
- 状态：待用户审阅
- 关联：主设计 `2026-10-03-film-radar-design.md` 第 11 节「我已经看过」、第 12 节调度、第 13 节失败处理、第 14 节未决事项⑤
- 分支：`feat/watched`

## 1. 目的与成功标准

**问题。** 现在的「我已经看过」按钮只存在当前浏览器的 `localStorage` 里：换设备就没了，流水线也不知道。结果是：

- 看过的片每期照样参加粗筛和精评，占入围名额、花精评费用。
- Issue 标题照样列出它们。Pan's Labyrinth 和 The Devils 连续三期都是重点推荐，三个 Issue 标题里都有。
- 手机和电脑上看到的「已看过」状态不一样。

**做什么。** 把「已看过」变成仓库里的一份名单（`data/watched.json`），作为唯一的事实来源。用户在 edition Issue 里勾选或取消勾选来标记；页面、所有 edition Issue、下一期的筛选都以这份名单为准。

**成功标准：**

1. 在任一期 edition Issue 里勾选或取消一部片，约两分钟内：名单更新；所有 edition Issue 里同一部片的勾选状态一致；页面（包括往期页面）显示一致。
2. 下一期粗筛之前就排除看过的片。仍在上映的列进「看过、仍在映」，不精评、不占名额。
3. 同步不调用 Claude，不产生费用。公开仓库的 Actions 分钟数免费。
4. 用户打的勾不会被静默丢掉：同步失败会开失败 Issue；出刊运行会读到还没同步的勾。

## 2. 已确认的决策（2026-10-17，用户）

| 问题 | 决定 |
|---|---|
| 在哪里标记 | 在 edition Issue 正文的勾选框里打勾（GitHub 网页或手机 App） |
| 看过的片下一期怎么处理 | 粗筛前排除，不再精评；页面底部和 Issue 里折叠列出「看过、仍在映」，方便撤销 |
| 什么时候生效 | 新增同步工作流，Issue 被编辑后一两分钟内同步，不等下一期 |
| 页面上的「我已经看过」按钮 | 去掉（保留会形成两份互相打架的记录）。「隐藏已看过」开关保留，它只是这台设备上的显示偏好 |
| 旧 Issue | 一次性把 #2、#4、#5（第 1、2、3 期）改成勾选格式；#3（10-04 被覆盖的重复一期）不动 |

**命名：** 代码里已有 `seen_before`，意思是「上一期也推荐过」，用来决定「新」徽标，和「看过」无关。新概念一律叫 **`watched`**，`seen_before` 及其逻辑不改。

## 3. 名单：`data/watched.json`

```json
{
  "version": 1,
  "films": {
    "62050": {
      "title": "Guillermo del Toro's Pan's Labyrinth 20th Anniversary",
      "since": "2026-10-17T14:03:00-04:00",
      "issue": 5
    }
  }
}
```

- 键是字符串形式的 `film_id`（JSON 的键只能是字符串）。同一部片在不同期的 `film_id` 不变，已核对三期数据：62050、62164 三期一致。
- `title` 方便人看；`since` 是同步记下它的时间（多伦多时区）；`issue` 是这个勾来自哪个 Issue。
- **撤销就是删掉这一条**，不留墓碑。历史在 git 提交记录里。
- 文件不存在等于空名单。**文件存在但格式不对，按失败处理，绝不当成空名单**：当成空名单的话，同步会把所有 Issue 里的勾全部清掉。
- **只有同步程序写这个文件。** 出刊运行只读它。

## 4. Issue 正文格式

```markdown
<!-- film-radar:edition 2026-10-22 -->
第 4 期重点推荐：

- [ ] **Fjord**（在映第 2 周）：一句话推荐…… <!-- film:62301 bot:0 -->

可以看：

- [ ] **Primetime**（10/24 上映）：一句话推荐…… <!-- film:62288 bot:0 -->
- [ ] **Dear You**（在映第 1 周）：一句话推荐…… <!-- film:62290 bot:0 -->

看过、仍在映（取消勾选可撤销）：

- [x] **Guillermo del Toro's Pan's Labyrinth 20th Anniversary** · 重映（2006 年上映） <!-- film:62050 bot:1 -->

跳过 50 部，未能评估 1 部。

勾选＝我已经看过，取消勾选＝撤销；改完约两分钟后页面和其他期 Issue 会同步。
完整页面：https://akasha-r.github.io/film-radar/
```

规则：

- 第一行的 `<!-- film-radar:edition <id> -->` 表示这是程序管理的 Issue，并说明是哪一期。**没有这行的 Issue 一律忽略**（#1 测试 Issue、#3 重复的一期、失败 Issue）。
- 每部片一行任务项，行尾的隐藏注释写着 `film_id` 和 **`bot`：程序最后一次写入时这一行勾没勾**。用户的操作靠比较「当前勾选」和 `bot` 得出，见第 5 节。
- 重点推荐、可以看两节都写成勾选框。重点推荐和可以看里如果有已看过的片（只在第 6 节所说的竞态下出现），也照名单打勾。
- 「看过、仍在映」一节列出当期因已看过而没参加评估、但仍在候选范围内（在映或即将上映）的片，写成已勾选（`bot:1`），片名后用「 · 」接状态（不用括号，`status_text` 自带括号）。这一节为空时不写。
- 标题格式不变（「第 N 期 M/D：重点推荐片名……」）。看过的片已经不参加评估，自然不会进标题。
- 所有来自数据的文字（片名、一句话推荐）照旧经过 `_no_mention`（防止 @ 到别人），**另外去掉 `<!--` 和 `-->`**，免得模型输出或片名里的字符伪造出标记。

**解析：**任务项行要匹配 `^- \[( |x|X)\] .*<!-- film:(\d+) bot:([01]) -->\s*$`。下面几种情况算这个 Issue **无法解析**，整个 Issue 跳过、一个勾都不采用，并按第 11 节报告：

- 有某一行含 `<!-- film:` 但不符合上面的格式（例如被手改坏了）；
- 同一个 `film_id` 在一个 Issue 里出现两次。

**整个 Issue 跳过、不做部分采用**：手改坏的 Issue 里分不清哪些勾是用户的意图。

## 5. 同步算法（纯函数，新模块 `watched.py`）

输入：所有带 `edition` 标签的 Issue（编号、正文、`updated_at`），当前名单，当前时间。

1. **解析**每个带 edition 标记的 Issue。无法解析的记进 `problems` 并跳过。
2. **找出用户的操作：**某一行「当前勾选 ≠ `bot`」，就是用户做过的操作。勾上了＝标为看过，取消了＝撤销。
3. **合并：**同一部片的操作如果在各 Issue 里一致，直接采用。不一致（一次同步之间，用户在一个 Issue 里勾上、在另一个里取消，很少见）时，**以 `updated_at` 最晚的那个 Issue 为准**，`updated_at` 相同再取编号大的。冲突写进运行摘要。
4. **得出新名单：**在旧名单上应用这些操作。
5. **得出要改写的 Issue：**对每个解析成功的 Issue 的每一行，目标状态＝这部片是否在新名单里；如果「当前勾选」或 `bot` 和目标状态不一致，两者都改成目标状态。只改这两个字符，正文其他部分原样保留（包括用户可能加的文字）。有变化的 Issue 才输出。

输出：新名单、操作清单、冲突清单、要改写的 Issue（编号、改写前正文、改写后正文）、`problems`。

**性质（都要有测试）：**

- **幂等：**同一份输入跑两遍，第二遍没有操作、没有改写。
- **名单是事实来源：**名单和某个 Issue 不一致、而那个 Issue 里也没有用户操作时（比如上次改写失败留下的旧状态），按名单改写 Issue，不会反过来改名单。
- 无法解析的 Issue 不影响其他 Issue。

## 6. 写入顺序（防止丢勾）

1. 计算（第 5 节）。
2. **名单有变化时，先写 `data/watched.json`、提交、推送**（推送被拒先 `pull --rebase` 再推，最多三次，和出刊工作流一样）。
3. 然后才改写 Issue。每改一个，先重新读取它的正文；**和计算时读到的不一样就跳过**（说明用户刚好又改了，那次编辑会触发下一次同步来处理），一样才提交改写。
4. 把 main 拉到最新，重新生成页面并部署。

**为什么先提交再改 Issue：**反过来的话，Issue 改写成功、提交却失败了，用户的那个勾在 Issue 里已经被「对齐」掉了，名单里却没有，这个勾就悄无声息地丢了。先提交的话，改写失败只会让 Issue 暂时显示旧状态，下一次同步会补上。

**残余风险：**第 3 步「重新读取」和「提交改写」之间有一个不到一秒的窗口，GitHub 的 Issue 接口不支持条件更新。用户恰好在这个窗口里打的勾会被覆盖。接受，写进第 15 节。

**出刊运行只读不写：**出刊运行开始时，用同一个纯函数在内存里算出「名单＋还没同步的勾」，用来排除候选。它不提交名单、不改 Issue。原因：出刊要跑十几分钟，期间同步工作流可能已经提交了新名单，两边都提交同一个文件会在变基时冲突。出刊运行结束后会触发一次同步（第 7 节），由同步负责提交和改写。

## 7. 工作流

### 新增 `.github/workflows/watched-sync.yml`

- **触发：**`issues: types: [edited]`；`workflow_dispatch`（手动，以及出刊运行结束时触发）。
- **过滤：**任务级 `if`：手动触发，或被编辑的 Issue 带 `edition` 标签。
- **并发：**`group: watched-sync`，`cancel-in-progress: false`。**不和出刊工作流共用并发组。**GitHub 的规则是：同一组里新排队的运行会取消原来排队的那个。共用的话，出刊运行排队时用户正好打勾，出刊运行就会被同步顶掉，而且不报错。同步自己被顶掉没关系：每次同步都是完整对账。
- **权限：**`contents: write`、`issues: write`、`pages: write`、`id-token: write`。
- **步骤：**
  1. 检出，安装 Python 3.11 和依赖。
  2. `python -m film_radar.main sync-watched`：读 Issue，计算，写 `data/watched.json` 和 `out/watched_plan.json`（要改写的 Issue），把操作、冲突、问题写进运行摘要。
  3. 名单有变化就提交、推送（同第 6 节）。
  4. `python -m film_radar.main apply-watched-rewrites`：按第 6 节第 3 步改写 Issue。
  5. 把 main 拉到最新，`build-site`，部署 Pages。**名单有变化，或是手动/出刊触发的运行，才部署**；只是对齐了 Issue 而名单没变，页面不用动。
  6. 失败时开失败 Issue（第 11 节）。

**页面不会被旧数据覆盖：**同步部署前会先把 main 拉到最新，但从拉取到部署之间，出刊运行仍可能刚好提交了新一期并完成部署，这时同步部署的是缺了新一期的页面。所以出刊运行在部署和开 Issue 之后，再**触发一次同步**。这次同步排在 `watched-sync` 组里，一定在之前那次之后执行，而且它是在新一期提交之后才开始的，所以最后一次部署的页面总是最新的。

### 修改 `.github/workflows/edition.yml`

- 「Run pipeline」步骤加上 `GITHUB_TOKEN` 和 `GITHUB_REPOSITORY` 环境变量，供第 6 节的只读计算使用。
- 开 Issue 之后新增一步：`gh workflow run watched-sync.yml`。需要新增权限 `actions: write`。
- 失败 Issue 的措辞增加一种处境：「新一期已经发布，只是同步没有触发。随便在一个 Issue 里勾一下，或者手动运行 watched-sync。」

## 8. 出刊流水线改动

- `main._run`：读 `data/watched.json`，再读 edition Issue，用第 5 节的纯函数算出「有效名单」（只在内存里）。读 Issue 失败时，以新环节「读取已看过名单」失败退出。**这一步在任何 Claude 调用之前，失败不花钱。**
- `run_pipeline(..., watched: set[int])`：
  - `check_sanity` 照旧用**排除前**的候选，「候选为 0」的含义不变。
  - 然后把候选分成两部分：看过的进 `watched_showing`，其余的继续。
  - `attach_details`、粗筛、精评只处理其余的部分，看过的片不抓详情页。
  - 其余部分为空时（所有候选都看过），粗筛直接返回空（`triage` 已经这样处理），这一期 0 部片，页面和 Issue 如实显示。
- edition 数据新增字段 `watched_showing`：每部包括 `film_id`、`title`、`status`、`release_date`、`weeks_in_release`、`film_url`（足够给 `status_text` 和链接用），按片名排序。**`counts` 和总数核对的含义不变**，只统计参加评估的片。老数据没有这个字段，按空列表处理。
- 跑的过程中用户撤销了某部片：这一期它仍然被排除了，下一期会正常参加评估。接受。

## 9. 页面改动

- `render_site(editions, out_dir, watched)`：名单里的片，在**所有页面**（包括往期）的卡片和速览行上，生成时就加上 `is-seen` 类和「✓ 已看过」角标，复用现有样式。
- **去掉**「我已经看过」按钮（`data-seen`）和它的点击、存储逻辑。按钮原来的位置换成链接「看过了？去 Issue 打勾」，指向 `https://github.com/<repo>/issues?q=is%3Aissue+label%3Aedition`。`config/settings.toml` 新增 `repo = "AKASHA-R/film-radar"`。
- **保留**「隐藏已看过」开关。计数改为数本页带 `is-seen` 的卡片，为 0 时不显示开关。偏好仍存在 `film-radar:hide-seen:v1`。旧键 `film-radar:seen:v1` 不再读取，也不删除。
- 新增折叠区「看过、仍在映（N）」，列出 `watched_showing`（片名、状态、Cineplex 链接）。放在「跳过的片」之后、「已过滤的非电影活动」之前。为空时不出现。
- 主设计第 11 节被测试钉住的约定继续成立：每部片的 `data-film` 在整页只出现一次；章节按首次出现的位置排序；`_STYLE_BASE` 保持原始字符串；页面始终浅色。
- 原来那个取舍「慢速网络下已看过的片会先闪一下」只剩「隐藏」这一种情况：已看过的样式在生成时就画好了，只有「隐藏」仍由脚本在页面末尾执行。
- 用户以前在浏览器里点过的标记**不迁移**（服务器读不到浏览器存储），需要在 Issue 里重新勾一次。

## 10. 旧 Issue 迁移

- 新 CLI 子命令：`migrate-issues --map 2=2026-10-03 --map 4=2026-10-04 --map 5=2026-10-08`。**默认只打印新正文**，加 `--apply` 才改写。
- 新正文用新版 `issue_body` 按对应那期的数据生成，期号按数据顺序算（第 1、2、3 期）。这时名单为空，所有片都不勾选。标题不改。
- 在本机用用户的身份执行（`GH_TOKEN` 取自 `gh auth token`）。用户身份的编辑**会**触发同步，这次同步应当没有任何操作、没有任何改写，正好顺便检验第 5 节的幂等性。
- #3 不动。它没有 edition 标记，同步会忽略它。
- GitHub 保留正文的编辑历史，改坏了可以从网页上恢复。

## 11. 失败处理

| 情况 | 处理 |
|---|---|
| 同步时 GitHub 接口出错，或推送三次都被拒 | 工作流失败，开失败 Issue（标签 `failure`，标题「已看过同步失败 日期」）。如果失败发生在提交之前，什么都没变；发生在提交之后、改写之前，Issue 暂时显示旧状态，下一次同步会补上 |
| 某个 Issue 无法解析 | 跳过它，其他 Issue 照常同步，工作流不算失败。开一个失败 Issue「已看过同步：Issue #N 无法解析」，写明是哪几行；**同标题的 Issue 还开着就不重复开** |
| `data/watched.json` 格式不对 | 失败，绝不当成空名单 |
| 同一部片在各 Issue 里的操作冲突 | 按第 5 节规则处理，写进运行摘要，不开 Issue |
| 出刊运行读取 Issue 失败 | 出刊失败，环节为「读取已看过名单」，这时还没有调用 Claude |
| 出刊运行结束时触发同步失败 | 出刊工作流的失败 Issue 按第 7 节的新措辞写 |

失败 Issue 带 `failure` 标签、不带 `edition` 标签，开 Issue 也不是「编辑」事件，所以不会触发同步，同步也会忽略它们。

## 13. 测试

全部不联网、不调 Claude；GitHub 接口用测试替身。

- **正文生成与解析：**生成后再解析，每部片的 `film_id`、勾选状态、`bot` 都对得上；带 `<!--`、`-->`、`@` 的片名和一句话推荐被清理；空小节不出现。
- **同步纯函数：**勾上；取消；名单与 Issue 不一致时按名单改写；冲突按 `updated_at` 决定、相同时按编号决定；无法解析的 Issue 被跳过且不影响其他；没有 edition 标记的 Issue 被忽略；幂等（第二遍无操作无改写）；只改勾选和 `bot` 两处，用户加的文字保留。
- **写入顺序：**用测试替身记录调用顺序，断言改写 Issue 一定在提交名单之后；重新读取到的正文变了就跳过、不提交改写。
- **`watched.json`：**不存在＝空；格式不对就抛错；写出的格式稳定（键排序、缩进），避免无意义的提交差异。

## 15. 风险与取舍

- **看过的片是公开的。**仓库是公开的（Pages 免费版要求），`data/watched.json` 和 Issue 里的勾任何人都看得到。口味档案本来就是公开的，这里多公开了「看过哪些片」。
- **读取到改写之间的窗口**（第 6 节）：不到一秒，GitHub 接口不支持条件更新。
- **手改 Issue 可能弄坏标记**：只影响那一个 Issue，会开失败 Issue 报告，不会静默。
- **两次部署挤在一起**：Pages 正在部署时又来一次部署，后一次可能失败。同步失败会开 Issue，下一次同步会重新部署。
- **排除是硬排除**：看过的片不会再被评估。想重新看到它的推荐卡，取消勾选，下一期就会重新评估。
