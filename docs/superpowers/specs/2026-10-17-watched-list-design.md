- 关联：主设计 `2026-10-03-film-radar-design.md` 第 11 节「已看过」、第 12 节调度、第 13 节失败处理、第 14 节未决事项⑤、第 16 节测试、第 17 节前提
- 分支：`feat/watched`

## 1. 目的与成功标准

**问题。** 现在的「我已经看过」按钮只存在当前浏览器的 `localStorage` 里：换设备就没了，流水线也不知道。结果是：

- 看过的片每期照样参加粗筛和精评，占入围名额、花精评费用。
- Issue 标题照样列出它们。Pan's Labyrinth 和 The Devils 连续三期都是重点推荐，三个 Issue 标题里都有。
- 手机和电脑上看到的「已看过」状态不一样。

**做什么。** 把「已看过」变成仓库里的一份名单（`data/watched.json`），作为唯一的事实来源。用户在 edition Issue 里勾选或取消勾选来标记；页面、所有 edition Issue、下一期的筛选都以这份名单为准。

**成功标准：**

1. 在任一期 edition Issue 里勾选或取消一部片，几分钟内：名单更新；所有 edition Issue 里同一部片的勾选状态一致；页面（包括往期页面）显示一致。同步本身一般一两分钟跑完；GitHub Pages 有最长 10 分钟的缓存（`max-age=600`），所以页面上看到变化可能要强制刷新。
2. 下一期粗筛之前就排除看过的片。仍在上映的列进「看过、仍在映」，不精评、不占名额。
3. 同步不调用 Claude，不产生费用。公开仓库的 Actions 分钟数免费。
4. 用户打的勾不会被静默丢掉。唯一不能完全消除的情况列在第 15 节，每一种都会开 Issue 报告，或者窗口不到一秒。

## 2. 已确认的决策（2026-10-17，用户）

| 问题 | 决定 |
|---|---|
| 在哪里标记 | 在 edition Issue 正文的勾选框里打勾（GitHub 网页或手机 App） |
| 看过的片下一期怎么处理 | 粗筛前排除，不再精评；页面底部和 Issue 里列出「看过、仍在映」，方便撤销 |
| 什么时候生效 | 新增同步工作流，Issue 被编辑后几分钟内同步，不等下一期 |
| 页面上的「我已经看过」按钮 | 去掉（保留会形成两份互相打架的记录）。「隐藏已看过」开关保留，它只是这台设备上的显示偏好 |
| 旧 Issue | 一次性把 #2、#4、#5（第 1、2、3 期）改成勾选格式；#3（10-04 被覆盖的重复一期）去掉 `edition` 标签并关闭 |
| 公开观影记录 | 用户 2026-10-18 明确接受：仓库是公开的，名单和 Issue 里的勾任何人都看得到，写进 git 历史后撤不回。见第 15 节 |

**命名：** 代码里已有 `seen_before`，意思是「上一期也推荐过」，用来决定「新」徽标，和「看过」无关。新概念一律叫 **`watched`**，`seen_before` 及其逻辑不改。

**「同一部片」按 Cineplex 的条目算。** 同一部电影的重映、周年纪念版，在 Cineplex 是另一个条目（另一组编号），会作为新片重新出现，需要再勾一次。

## 3. 名单：`data/watched.json`

```json
{
  "version": 1,
  "films": {
    "62050": {
      "title": "Guillermo del Toro's Pan's Labyrinth 20th Anniversary",
      "since": "2026-10-17T14:03:00-04:00",
      "ids": [62050]
    }
  }
}
```

- 键是勾选那一刻这部片的 `film_id`（主条目编号），写成字符串（JSON 的键只能是字符串）。**加载函数一次性把键和 `ids` 转成整数**，其他代码只见整数。
- **`ids` 是这部片所有版本的编号。** 候选是把同名的多个版本合并成一部片，主条目编号取合并后的第一个，而版本集合在真实数据里会变（Street Fighter 第 3 期多了版本 62252；Digger、Forgotten Island 少了版本）。所以判断「看过」不只看主编号：**候选的任一版本编号在任一条目的 `ids` 里，就算看过。** 同步记录一部片时，从 `data/editions/` 里所有以它为主条目的期次收集版本编号。
- `title` 方便人看；`since` 是第一次记下它的时间（多伦多时区）。**已经在名单里的片再被勾一次，不改动已有条目**（不刷新 `since`），避免无意义的提交。
- **撤销就是删掉这一条**，不留墓碑。历史在 git 提交记录里。
- 写出格式固定（键排序、缩进 1），避免无意义的差异。
- 文件不存在等于空名单。**文件存在但格式不对，按失败处理，绝不当成空名单**：当成空名单的话，同步会把所有 Issue 里的勾全部清掉。
- **只有同步程序写这个文件。** 出刊运行只读它。

## 4. Issue 正文格式

```markdown
<!-- film-radar:edition 2026-10-22 -->
第 4 期重点推荐：

- [ ] **Fjord** · 在映第 2 周：一句话推荐…… <!-- film:62301 bot:0 -->

可以看：

- [ ] **Primetime** · 10/24上映：一句话推荐…… <!-- film:62288 bot:0 -->
- [ ] **Dear You** · 在映第 1 周：一句话推荐…… <!-- film:62290 bot:0 -->

看过、仍在映（取消勾选可撤销）：

- [x] **Guillermo del Toro's Pan's Labyrinth 20th Anniversary** · 重映（2006 年上映） <!-- film:62050 bot:1 -->

跳过 50 部，未能评估 1 部。

勾选＝我已经看过，取消勾选＝撤销。几分钟后页面和其他期 Issue 会同步；页面没变化就强制刷新一下。
完整页面：https://akasha-r.github.io/film-radar/
```

规则：

- 第一行的 `<!-- film-radar:edition <id> -->` 表示这是程序管理的 Issue，并说明是哪一期。**没有这行的 Issue 一律忽略。**
- 每部片一行任务项，行尾的隐藏注释写着 `film_id` 和 **`bot`：程序最后一次写入时这一行勾没勾**。用户的操作靠比较「当前勾选」和 `bot` 得出，见第 5 节。
- 片名和状态之间用「 · 」分隔，所有行都一样（`status_text` 对重映会返回带括号的文字，外面再套括号就成了双层括号）。
- 重点推荐、可以看两节都写成勾选框。这两节里如果有已看过的片（只在第 8 节说的「运行中途撤销」时出现），也照名单打勾。
- 「看过、仍在映」一节列出当期因已看过而没参加评估、但仍在候选范围内（在映或即将上映）的片，写成已勾选（`bot:1`）。这一节为空时不写。
- **不用 `<details>` 折叠**：折叠块里的任务项在 GitHub 上可能点不了，还会影响同一 Issue 里的其他勾选框。
- 标题格式不变（「第 N 期 M/D：重点推荐片名……」）。看过的片已经不参加评估，自然不会进标题。
- **来自数据的文字（片名、一句话推荐）一律清理**：换行、制表符换成空格（否则一行任务项会被拆成两行，整个 Issue 生来就无法解析）；`<`、`>` 换成全角「＜」「＞」（防止伪造出注释标记，逐字替换不会像「删掉 `<!--`」那样拼出新的标记）；照旧经过 `_no_mention`（防止 @ 到别人）。

**解析：**任务项行要匹配 `^- \[( |x|X)\] .*<!-- film:(\d+) bot:([01]) -->\s*$`。下面几种情况算这个 Issue **无法解析**，整个 Issue 跳过、一个勾都不采用，并按第 11 节报告：

- 有某一行含 `<!-- film:` 但不符合上面的格式（例如被手改坏了）；
- 同一个 `film_id` 在一个 Issue 里出现两次。

整个 Issue 跳过、不做部分采用：手改坏的 Issue 里分不清哪些勾是用户的意图。

## 5. 同步算法（纯函数，新模块 `watched.py`）

**读取：**列出仓库里**所有**带 `edition` 标签的 Issue：`state=all`（**包括已关闭的**，用户可能勾完顺手关掉），按页读完（每页 100，跟着 `Link` 头翻页），去掉 Pull Request。每个 Issue 取编号、正文。

1. **解析**每个带 edition 标记的 Issue。无法解析的记进 `problems` 并跳过。
2. **找出用户的操作：**某一行「当前勾选 ≠ `bot`」，就是用户做过的操作。勾上了＝标为看过，取消了＝撤销。
3. **合并：**同一部片的操作如果在各 Issue 里一致，直接采用。不一致（一次同步之间，用户在一个 Issue 里勾上、在另一个里取消，很少见）时，**以编号大的 Issue（较新的一期）为准**，冲突写进运行摘要。不用 Issue 的 `updated_at`：评论、关闭、改标签都会刷新它，反映不了勾选的先后。
4. **得出新名单：**在旧名单上应用这些操作。勾上一部已在名单里的片，不改动；取消一部不在名单里的片，不改动。
5. **得出改写计划：**对每个解析成功的 Issue 的每一行，目标状态＝这部片是否在新名单里（按第 3 节的 `ids` 匹配）。如果「当前勾选」或 `bot` 和目标状态不一致，就列入计划。计划里同时记下**计算时读到的勾选**（第 6 节第 4 步要用）。

输出：新名单、操作清单、冲突清单、改写计划、`problems`。

**性质（都要有测试）：**

- **幂等：**同一份输入跑两遍，第二遍没有操作、没有改写。
- **名单是事实来源：**名单和某个 Issue 不一致、而那个 Issue 里也没有用户操作时（例如上次改写失败留下的旧状态），按名单改写 Issue，不会反过来改名单。
- 无法解析的 Issue 不影响其他 Issue。
- 没有 edition 标记的 Issue（测试 Issue、失败 Issue、#3）被忽略。

## 6. 同步的执行顺序（防止丢勾）

每次同步运行都做完整的一轮：

1. **检出最新的 main**（`actions/checkout` 加 `ref: main`）。不能用默认值：`issues` 和 `workflow_dispatch` 事件的运行在**创建时**就固定了要检出的提交，在并发组里排队的运行等到开始执行时，检出的是好几分钟前的旧名单，会按旧名单把刚同步好的 Issue 改回去。
2. 读取并计算（第 5 节）。
3. **名单有变化时，先提交 `data/watched.json` 并推送。**推送被拒就 `pull --rebase` 再推，最多三次。同步运行之间是串行的，只有同步写这个文件，所以变基不会在这个文件上冲突（出刊运行只提交 `data/editions/`）。
4. **然后才改写 Issue。**对计划里的每个 Issue：重新读取正文，在**新读到的正文**上逐行合并（按 `film_id` 对应）：
   - `bot` 一律写成目标状态；
   - 勾选框**只有在「新读到的勾选」等于「计算时读到的勾选」时**才改成目标状态，否则保留用户刚改的勾选。这样，用户在计算之后又反悔（勾了马上取消，或者反过来），那一行会变成「当前 ≠ `bot`」，下一次同步能认出来；
   - 重新读取时已无法解析的 Issue 跳过并报告。

   接口出错的改写重试三次；仍然失败的，在这一轮结束时让运行失败并开失败 Issue（第 11 节）。
5. **把 main 拉到最新，生成页面并部署。每次同步都部署**，不管名单变没变。

**为什么先提交再改 Issue：**反过来的话，Issue 改写成功、提交却失败了，用户的那个勾在 Issue 里已经被「对齐」掉，名单里却没有，这个勾就悄无声息地丢了。先提交的话，改写失败只会让 Issue 暂时显示旧状态，下一次同步会补上（例外见第 15 节）。

**这个顺序由代码保证，不靠文字：**第 3、4 步是工作流里的两个步骤，第 4 步的 `if` 依赖第 3 步成功。有一条 pytest 读取工作流 YAML，断言检出带 `ref: main`、提交步骤在改写步骤之前、改写步骤以提交成功为条件（第 13 节）。

**为什么每次都部署、而且只有同步部署：**

- **页面只由同步工作流部署，出刊工作流不再部署页面。**出刊运行提交新一期之后触发一次同步，由那次同步生成并部署页面。这样整个仓库只有一个部署者，不会出现两个工作流同时部署 Pages、其中一个失败的情况。
- 同步运行在一个并发组里串行执行，每次都从最新的 main 开始，而且每次都部署，所以**后一次部署一定不比前一次旧**。GitHub 的规则是同组里新排队的运行会取消原来排队的那个，但被取消的和顶替它的做的是同一件事，而且顶替者开始得更晚。
- 代价：新一期的页面比 Issue 晚一两分钟更新；每次编辑 Issue 都会部署一次（免费，约半分钟）。

**出刊运行只读不写：**出刊运行用同一个纯函数在内存里算出「名单＋还没同步的勾」，用来排除候选和生成新 Issue 的勾选状态。它不提交名单、不改 Issue。原因：出刊要跑十几分钟，期间同步可能已经提交了新名单，两边都提交同一个文件会在变基时冲突。出刊运行最后触发的那次同步负责提交和改写。

**连续在没刷新的页面上勾选：**同步改写 Issue 之后，用户如果在没刷新的页面上接着勾下一个，GitHub 的处理方式可能是按位置只改那一项、用页面上的旧正文整份覆盖，或者拒绝。前两种不需要改设计：同步从不增删行，被旧正文覆盖回来的那些行，勾选和 `bot` 是一致的，同步会当作「没有操作」再按名单改回来；用户新勾的那一项照常是操作。第三种由闸门 G1、G2 实测后决定提示语（第 12 节）。

## 7. 工作流

### 新增 `.github/workflows/watched-sync.yml`

- **触发：**`issues: types: [edited]`；`workflow_dispatch`（手动，以及出刊运行最后触发）。
- **不加任务级的过滤条件。**任何 Issue 被编辑都跑一轮完整同步。如果只对带 `edition` 标签的 Issue 运行，编辑别的 Issue 产生的运行仍会进入并发组、顶掉排队中的那次同步，自己却什么都不做，那次部署就丢了。非 edition Issue 的编辑很少，多跑一轮没有坏处。
- **并发：**工作流级 `group: watched-sync`，`cancel-in-progress: false`。**不和出刊工作流共用并发组**：共用的话，出刊运行排队时用户正好打勾，出刊运行就会被同步顶掉，而且不报错。
- **权限：**`contents: write`、`issues: write`、`pages: write`、`id-token: write`。任务声明 `environment: github-pages`（部署 Pages 必需）。
- **步骤：**
  1. 检出 main（`ref: main`），安装 Python 3.11 和依赖。
  2. `python -m film_radar.main sync-watched`：读 Issue，计算，写 `data/watched.json` 和 `out/watched_plan.json`（改写计划），把操作、冲突、问题写进运行摘要。
  3. 名单有变化就提交、推送（第 6 节第 3 步）。
  4. `python -m film_radar.main apply-watched-rewrites`：按第 6 节第 4 步改写 Issue。
  5. 把 main 拉到最新，`build-site`，部署 Pages。
  6. 无法解析的 Issue：开（或不重复开）失败 Issue，工作流本身不算失败。
  7. 失败时开失败 Issue（第 11 节）。

### 修改 `.github/workflows/edition.yml`

- 「Run pipeline」步骤加上 `GITHUB_TOKEN` 和 `GITHUB_REPOSITORY` 环境变量，供第 8 节的只读计算使用。
- **去掉** `configure-pages`、`upload-pages-artifact`、`deploy-pages` 三步，以及任务上的 `environment: github-pages` 和 `pages`、`id-token` 权限。
- 开 Issue 的步骤加 `id: issue`。之后新增一步 `id: dispatch`：`gh workflow run watched-sync.yml --ref main`，条件是 `always() && steps.commit.outcome == 'success'`。开 Issue 失败也要触发，否则页面就没人更新了。新增权限 `actions: write`。
- 失败 Issue 的措辞按下面的顺序判断（先命中先用），对应的步骤结果作为环境变量传进去：
  1. 提交成功、触发同步失败：「新一期数据已提交，但页面还没更新（同步没有触发）。手动运行 watched-sync，或者在任意一个 Issue 里勾一下。」开 Issue 也失败时补一句「通知 Issue 也没开成」。
  2. 提交成功、开 Issue 失败、触发同步成功：「页面会在几分钟内更新到新一期，只是通知 Issue 没开成。」
  3. 其余情况沿用现有措辞（流水线失败读 `out/failure.txt`、推送被拒、环境准备失败）。现有的「部署失败」分支删掉，因为出刊运行不再部署。

## 8. 出刊流水线改动

- **顺序：**先过双周门控（跳过周照旧什么都不做、不建任何客户端、不读 GitHub），然后读 Issue，再从 `origin/main` 取最新的 `data/watched.json`（`git fetch` 后读取，不用检出时的那份），用第 5 节的纯函数算出「有效名单」（只在内存里）。**先读 Issue、后读名单**：同步是先提交名单、后改写 Issue，所以读 Issue 在前时，任何一个勾要么还在 Issue 里显示为操作，要么已经在后读到的名单里；反过来先读名单的话，两次读取之间刚好完成一次同步，会同时漏掉两边的这个勾。（2026-10-18 实施时的任务审查纠正：此前版本把顺序写反了。）
- **注入：**`_run` 像 `build_clients` 那样通过一个可替换的 `issue_reader` 取 Issue，测试里换成替身，不联网。没有 `GITHUB_TOKEN`（例如本机手动跑）时按失败处理，不悄悄只用文件里的名单。
- **失败环节：**新增异常类 `WatchedError`（名单格式不对）和 `GitHubError`（接口出错），登记进 `STAGES`，环节名分别是「读取已看过名单」「GitHub 接口」，照旧写 `out/failure.txt`。这一步在任何 Claude 调用之前，失败不花钱。`sync-watched`、`apply-watched-rewrites`、`migrate-issues` 三个新子命令共用 `main()` 的异常处理，同步工作流的失败 Issue 也读 `out/failure.txt`。
- `run_pipeline(..., watched: frozenset[int] = frozenset())`（给默认值，现有测试不用改）：
  - `check_sanity` 照旧用**排除前**的候选，「候选为 0」的含义不变。
  - 然后把候选分成两部分：任一版本编号在有效名单里的，进 `watched_showing`；其余的继续。
  - `attach_details`、粗筛、精评只处理其余的部分，看过的片不抓详情页。
  - 其余部分为空时（所有候选都看过），粗筛直接返回空（`triage` 已经这样处理），这一期 0 部片，页面和 Issue 如实显示。

## 11. 失败处理

所有失败 Issue 都带 `failure` 标签、不带 `edition` 标签，正文末尾带 `cc @<仓库所有者>`（和现有失败 Issue 一样，靠它确保通知）。**同标题的失败 Issue 还开着就不重复开，而是把这次的情况追加为它下面的一条评论**（评论同样带 cc，会通知）；只有「Issue 无法解析」的通知在同标题 Issue 开着时直接跳过（它的内容不变，每次编辑 Issue 都追加评论会刷屏）。不能只跳过：没有任何步骤会关掉失败 Issue，一个旧的「已看过同步失败」开着，就会让之后的每次同步失败悄无声息，包括第 15 节依赖的改写失败提醒。用 REST 接口列出 `labels=failure&state=open` 的 Issue 逐个比较标题，不用搜索接口（搜索索引有延迟，连续两次同步仍会重复开）。列不出来时照常新开（宁可重复，不能漏报）；追加评论失败（比如 Issue 被锁）时也改为新开。实现在 `scripts/open_issue_once.sh`。

| 情况 | 处理 |
|---|---|
| 同步读 Issue 出错，或推送三次都被拒 | 运行失败，开「已看过同步失败」。名单没提交，什么都没变；用户的勾还在 Issue 里，下一次同步会补上 |
| 名单已提交，改写 Issue 重试三次仍失败 | 运行失败，开「已看过同步失败」，写明哪几个 Issue 没改完，并提醒：**下一次同步成功之前，不要在这几个 Issue 里撤销刚才的勾**（会被认成「没有操作」，见第 15 节）。手动运行 watched-sync 即可 |
| 名单已提交、Issue 已改写，部署失败 | 运行失败，开「已看过同步失败」，写明「名单和 Issue 已经更新，只是页面还是旧的；手动运行 watched-sync 重新部署」 |
| 某个 Issue 无法解析 | 跳过它，其他 Issue 照常同步，工作流不算失败。开「已看过同步：Issue #N 无法解析」，写明是哪几行 |
| `data/watched.json` 格式不对 | 失败，绝不当成空名单 |
| 同一部片在各 Issue 里的操作冲突 | 按第 5 节规则处理，写进运行摘要，不开 Issue |
| 出刊运行读取名单或 Issue 失败 | 出刊失败，环节为「读取已看过名单」或「GitHub 接口」，这时还没有调用 Claude |
| 出刊运行最后触发同步失败、开 Issue 失败 | 见第 7 节的措辞顺序 |

失败 Issue 被开出来不是「编辑」事件，不会触发同步。用户编辑失败 Issue 会触发一次同步，按第 7 节，这次同步照常完整执行，没有坏处。

## 15. 风险与取舍

- **看过的片是公开的。**仓库是公开的（Pages 免费版要求），`data/watched.json` 和 Issue 里的勾任何人都看得到，写进 git 历史后撤不回。口味档案本来就是公开的，这里多公开了「看过哪些片」。**用户已于 2026-10-18 明确接受。**
- **改写失败之后、下一次同步成功之前，在同一个 Issue 里撤销刚才的勾会被吞掉。**那一行停在「已勾、`bot` 为未勾」，名单里已经有这部片；用户此时取消，那一行变成「未勾、`bot` 为未勾」，同步认不出是操作，会按名单再勾回去。要彻底消除，需要在名单里记下每个 Issue 每一行已被吸收的状态，复杂度不值。缓解：改写失败会重试三次，仍失败就开失败 Issue 并写明这个提醒；被勾回去之后用户再取消一次就能正常撤销。
- **读取到改写之间的窗口**（第 6 节第 4 步）：重新读取和提交改写之间不到一秒，GitHub 的 Issue 接口不支持条件更新。用户恰好在这个窗口里打的勾会被覆盖。
- **手改 Issue 可能弄坏标记**：只影响那一个 Issue，会开失败 Issue 报告，不会静默。
- **页面比 Issue 晚：**新一期的 Issue 先开，页面要等随后的同步部署，晚一两分钟；Pages 缓存最长 10 分钟。
- **排除是硬排除**：看过的片不会再被评估。想重新看到它的推荐卡，取消勾选，下一期就会重新评估。
